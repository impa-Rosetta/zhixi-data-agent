## 一 可直接改写的 S1 方案概要

制造企业已经沉淀生产、质量、设备和库存等数据，但业务人员通常只熟悉“良率”“缺陷”“停机”等业务语言，不熟悉数据表、字段、SQL 和指标公式。一次分析往往要经过人工找数、确认口径、写查询、制作图表和解释结果，响应慢且难以复用。智析 Data Agent 面向这一断层，将数据目录、业务知识、语义指标和受控分析工具组合成自然语言问析平台。管理员通过只读连接接入已有数据源，系统扫描表、字段和关系，确认物理数据与业务语义的映射；用户提问后，Agent 识别意图与上下文，选择目录检索、指标查询、统计、图表或报告工具，经过权限检查、只读执行和结果验证后，以文字、表格、图表及证据引用呈现结论。用户可在同一会话继续追问、比较或补充条件。产品以版本化指标口径、确定性 SQL 编译和可追溯 Evidence 限制模型的不确定性，既降低企业数据底座的使用门槛，也为后续扩展生产、设备、库存和建模场景提供可复用的技术基础。

这一版本约 500 字，主笔可按正式版功能状态和 800 字上限再压缩或微调。若报告导出或建模尚未实机验收，S1 的“报告工具”应改为“逐步接入的报告能力”，不要把规划能力放在已完成效果里。

## 二 产品定位与业务问题

### 产品定位

智析 Data Agent 是部署在企业数据底座之上的可信自助问析产品。它不替代 ERP、MES、QMS 或设备管理系统，而是从这些系统汇集后的标准数据表中读取已授权数据，建立业务语义，再让用户以对话方式调用分析能力。它也不是只能回答预设问题的聊天页面：每一轮分析都要有任务类型、可检查的计划、受限工具调用、真实数据结果和可回溯依据。

### 目标客户与使用者

目标客户是已建设数据底座或正在推进数据治理的制造企业及其数字化服务商。质量人员分析不良率、一次通过率和缺陷结构；生产人员分析工序产量与良率；设备人员关心停机与运行效率；管理人员希望快速获得周报、月报和专题分析；数据管理员负责连接数据源、确认语义映射和发布指标口径。

### 需要解决的五个具体问题

1. 业务名称与数据库名称不一致，普通用户不知道应查哪张表、哪个字段。
2. 相同指标在不同部门容易出现公式、时间粒度或过滤条件不一致。
3. 临时分析依赖工程师手工编写 SQL、统计代码和图表，重复劳动多。
4. 自由生成的 SQL 或脚本可能越权、写入数据、扫描过大或给出无法复核的数字。
5. 单轮查询和静态报表难以支持“按月展开、对比上期、解释异常”这样的连续业务分析。

### 服务流程

数据管理员接入只读 PostgreSQL 或 MySQL 数据源，扫描并发布版本化目录；系统展示表、字段、类型、说明、样例值、关系及安全画像；管理员确认物理字段和业务对象、指标、规则的对应关系并发布语义版本。业务用户创建会话并提问，Agent 识别任务、绑定语义、生成声明式计划、选择工具执行，经安全验证后展示自然语言结论、表格、图表和证据。用户继续追问时，系统只继承已验证且获授权的上下文。

## 三 产品亮点与写作依据

### 亮点一 面向未知数据资源而非写死演示表

系统通过连接器读取真实数据库的表、字段、约束、关系和版本差异，借助安全采样与字段画像辅助理解未知结构。模型可以提出语义候选，最终由管理员确认映射并运行可行性验证。标准库、字段改名库、缺字段库三类样例可分别证明正常执行、适配能力和受控失败。这一亮点直接对应官方“面向未知数据表和业务资源”的要求。当前核心目录、画像和映射流程已完成；报告中不要声称任意数据库无需配置即可立即自动分析。

### 亮点二 业务语义约束指标口径

系统把制造质量业务对象、维度、规则、分析主题和十九项指标组织成版本化语义模型。大模型理解“最近三个月不良率”这类业务表达，确定性程序负责已发布指标的公式、字段路径、时间范围和 SQL 编译。这样能够减少模型猜字段、算错比率和不同会话口径漂移。制造质量模板和核心语义发布已实现；生产、设备和库存的完整语义包属于扩展计划。

### 亮点三 Agent 自主选工具但执行受控

Agent 按“理解问题、绑定语义、形成计划、选工具、执行、验证、解释”的流程运行。工具注册层声明能力、输入输出契约、权限和风险边界。模型负责意图、规划与表达，程序负责权限、指标、查询和数值验证。这样既保留 Agent 针对不同问题选择路径的灵活性，也让每一步可审计。已有 DeepSeek 网关、Planner、工具契约和 LangGraph 主链路；复杂建模工具仍需后续完善。

### 亮点四 连续对话与自然澄清

用户可以在同一会话中提出新问题、按月份展开、画图或与上期比较。澄清、权限不足、数据不足和执行异常由 Agent 用自然语言说明，底部输入框保持可用。Conversation、Turn 和 AnalysisRun 分开持久化，页面刷新或网络中断后能恢复记录。此能力已有验收；主笔可用真实会话截图展示，不宜用静态 AI 效果图替代。

### 亮点五 结果、图表和报告都有依据

数字结果关联查询产物、语义版本、验证记录和 Evidence，用户可以定位其来源。描述统计与受限 ChartSpec 只从已验证查询产物派生，前端以 ECharts 渲染折线、柱状、横向柱状和散点，不执行模型生成的 JavaScript。报告方案只接受可信产物，生成 Markdown、HTML、PDF 并保留引用。图表已通过真实链路验收；报告服务端生成达到代码级验收，面向用户的完整导出和容器中文 PDF 仍须在交稿前复核。

### 亮点六 企业安全与工程可用性

系统使用工作空间隔离和服务端权限策略，数据库连接只读，凭据加密存储。语义查询经参数化编译和 SQL AST 安全门禁，再由验证 ID 执行；任务支持超时、取消、幂等、审计和恢复。模块化单体配合独立 Worker、PostgreSQL、Redis、MinIO 和容器部署，适合逐步落地。主笔可把它写成“具备企业产品基础”，不要将未经性能、安全、备份恢复和生产运维验收的能力描述为“已达生产级认证”。

## 五 技术框架与组件职责

### 总体架构

系统采用“Web 前端 + FastAPI 模块化单体 + Celery Worker + 独立分析执行边界”的架构。交互层承担登录、数据治理、语义管理、自然语言会话、图表与证据展示；Agent 编排层承担任务识别、计划、工具路由和状态恢复；业务语义层定义对象、指标、规则及物理映射；查询分析层完成安全 SQL、统计、受限图表、报告和将来的建模；数据治理层负责连接、扫描、画像和目录版本；平台层提供权限、审计、数据库、队列、对象存储与部署。

| 层级 | 主要模块 | 输入与输出 |
| --- | --- | --- |
| 交互层 | React、TypeScript、Vite、React Query、ECharts | 用户问题、数据管理操作；自然语言、表格、图表、证据 |
| Agent 编排层 | DeepSeek 模型网关、LangGraph、Planner、Tool Registry | 意图与会话上下文；声明式计划、工具结果、回答 |
| 业务语义层 | 版本化对象、指标、维度、规则、映射工作台 | 物理目录；已发布的业务口径 |
| 查询分析层 | SQL 编译器、SQLGlot、安全执行、统计、ChartSpec、报告 | 结构化分析请求；可信查询及派生产物 |
| 数据治理层 | PostgreSQL/MySQL 连接器、目录扫描、安全画像 | 企业只读数据；目录快照、关系和字段信息 |
| 平台基础层 | FastAPI、PostgreSQL、Redis、Celery、MinIO、Alembic、Docker Compose | 身份权限、事务、任务、文件与部署 |

模块化单体保持业务事务和数据契约集中，耗时扫描与分析交给独立 Worker。后续脚本与机器学习任务放入一次性隔离沙箱，不能在 API 进程或业务数据库主机上直接运行。模型网关隔离 DeepSeek 供应商细节，未来可替换其他符合契约的大模型。

### 关键数据对象

Workspace 保存团队隔离边界；DataSource 保存加密连接配置；CatalogSnapshot 保存不可变的表字段目录；SemanticModelVersion 保存已发布业务语义；Conversation 保存持续对话；Turn 保存用户与 Agent 的每轮交互；AnalysisRun 保存每轮不可变执行；Artifact、Validation 和 Evidence 保存结果、校验与来源；Report 保存从可信结果组装的报告及文件元数据。这些对象的分层让交互连续，执行仍可独立复现。

### 端到端技术路径

“只读数据源 → 目录扫描与安全画像 → 管理员确认语义映射 → 发布指标版本 → 用户自然语言提问 → 意图与上下文识别 → 结构化计划 → 能力与工具选择 → 权限和 SQL 安全检查 → 查询及统计图表工具 → 结果验证和证据记录 → 自然语言回答 → 同一会话追问”。主笔绘制架构图或流程图时应按此顺序，不要画成“问题直接送入大模型，再由大模型直接访问数据库”。

## 六 Agent 的工具选择与多轮机制

### 模型与程序的职责分界

大模型负责理解自然语言、识别歧义、生成受约束的计划、选择候选能力和组织人类可读回答。确定性程序负责工作空间权限、发布语义、指标公式、SQL 编译、参数绑定、只读执行、统计计算、结果核对和证据写入。模型不接触数据库凭据，不能自己决定扩大授权范围，也不能直接执行其输出的任意脚本。

### 典型工具族

目录与语义工具负责搜索表字段、查看关系、查找业务对象和指标；查询工具负责生成结构化语义查询、编译与验证 SQL、只读执行；分析工具负责统计、趋势、排行、比较、相关性和计划中的模型任务；可视化工具将验证结果组合为受限 ChartSpec；报告工具将可信产物编排成带来源的文件；治理工具负责权限、审计和任务状态。不同问题触发不同组合，模型不会把所有请求强行转成 SQL。

### 问题处理示例

用户问“最近三个月不良率趋势”。Agent 识别不良率指标、三个月时间范围和按月粒度；语义模型解析指标公式与唯一时间字段；Planner 选择指标查询、统计和折线图工具；查询编译器生成参数化 SQL，通过 AST 与权限校验后在只读事务中执行。系统返回三个月的真实数据、折线图、文字结论以及 Evidence。用户接着说“按月份展开”或“和上月比”，系统在同一会话继承已验证指标和时间语义，只修改分析维度与比较任务。若某些月份缺失，回答必须说明数据不足，不能把单点画成趋势。

### 澄清与失败处理

当“良率”对应多个指标、时间范围不明确、缺少必要字段或用户无权限时，Agent 用自然语言问清问题或说明限制，并尽可能给出可执行的下一步。内部错误码留在技术详情，不直接暴露给普通用户。若模型服务或队列暂时不可用，系统保留会话与运行状态并按受控策略恢复。

## 七 数据治理 业务语义与可信执行

### 数据资源理解

连接器读取 PostgreSQL 和 MySQL 的 Schema、表、字段、类型、注释、主外键、约束和索引。扫描完成后发布不可变目录快照，支持版本差异查看。安全画像在管理员授权和预算限制下提供空值率、估算基数、范围及脱敏样例，用于帮助理解字段。字段敏感性不明确时保守处理，原始敏感值不进入模型上下文或日志。

### 制造质量语义

首发质量模型涵盖工厂、产线、产品、工单、批次、设备、检验和缺陷等对象，以及不良率、一次通过率、返工率等十九项已定义指标。每个指标记录公式、单位、聚合方式、时间与分组维度、别名、物理字段映射和版本。发布前检查关系路径与字段可用性。报告附录可以选两三个指标写出完整口径，避免只展示“十九项”数量却无法解释怎么算。

### SQL 与脚本执行

常规指标问题使用结构化语义查询和确定性双数据库 SQL 编译器。生成语句可供有权限人员查看，但执行前必须通过 SQL AST 门禁、表字段授权、参数化、只读事务、超时和行数限制。复杂自定义统计或建模脚本在完整产品中放入无网络、非 root、只读输入的一次性沙箱，并限制 CPU、内存、时间和输出文件。该沙箱及六类指定模型目前属于计划，不应在当前原型效果中伪造代码执行截图。

### 结果证据

每次分析冻结数据目录快照、语义版本、工具版本和运行标识。查询结果、统计、图表和报告分别成为 Artifact，并关联 Validation 与 Evidence。面向业务人员展示简洁结论，面向管理员提供可展开的查询与验证详情。报告里的数字不得脱离对应查询结果单独编造。

| 评测与观测 | 黄金问题集、正确率、安全、延迟、成本、链路追踪 | 系统化评测中心与观测规划中 |
| 产品加固 | 性能、备份、升级、生产部署与完整材料 | 计划在后续里程碑完成 |

“代码完成”与“用户已经能在网页稳定使用”不是同一件事。最终提交前，组长应运行固定演示脚本，再由主笔据实把相关行改为“已实机验收”或保留“开发中”。

## 九 典型场景与建议演示脚本

### 场景一 数据资源理解

管理员接入样例 PostgreSQL 或 MySQL 数据源，查看表、字段、关系和画像，再展示业务语义映射。其证明点是 Agent 知道“有什么数据”和“业务词对应哪里”。建议保留目录页、字段详情页、语义指标页的真实截图。

### 场景二 质量指标与连续追问

业务用户问“最近三个月不良率趋势”，系统展示按月数据、折线图和依据。随后追问“按月份展开”“和上月比”“解释这个变化”，显示同一会话中的上下文继承和澄清。选择固定样例数据并事先核对预期数字，避免视频和报告中出现不同结论。

### 场景三 不良产品排行

用户问“找出最近一个月不良数量最高的产品”，Agent 绑定产品维度和不良数量指标，返回排行、表格和可定位的查询依据。若实际样例数据不支持该时间范围，就改用已验收的固定问题，不要在录制当天临时编问题。

### 场景四 未知数据源适配

连接字段改名的样例库，展示目录差异、候选映射、管理员确认和语义验证。再用相同业务问题得到结果。此场景突出平台不是对固定表名的硬编码。

### 场景五 周报与完整产品路线

完整方案中，Agent 应把多个可信查询、统计和图表组装成周度质量报告，并提供 Markdown、HTML、PDF。当前服务端报告生成核心已有代码级验收，但视频是否演示下载，以最终网页和容器实机验收为准。若尚未打通，应展示已完成的问析与图表，然后在路线图中说明报告导出后续收口。

### 十分钟讲述顺序建议

第 0 至 1 分钟说明企业已有数据却难自助分析；第 1 至 2 分钟介绍定位和价值；第 2 至 4 分钟展示数据资源与语义；第 4 至 7 分钟实机演示连续问析、工具过程、图表和证据；第 7 至 8 分钟展示安全与架构；第 8 至 9 分钟讲亮点及行业应用；第 9 至 10 分钟说明真实完成状态、后续规划和总结。录屏路线应以最终冻结版本调整。

## 十 S2A 至 S2D 可直接扩写的内容

### S2A 目标与服务模型

智析的服务对象是已经有数据底座、但业务自助分析能力不足的制造企业。产品通过“数据接入与理解—业务语义发布—自然语言问析—可信结果与追问”的服务流程，把数据工程师反复执行的取数与报表步骤沉淀为可复用工具。质量、生产、设备和管理岗位共享同一入口，但只看到各自获授权的数据与能力。首发以制造质量为可复现领域，后续通过新增语义包和连接器扩展，而不是为每个客户重新写一个聊天机器人。服务价值应从需求响应时间、重复报表工作量、指标口径一致性和分析可复核性四个维度评估；正式数字须在试点后实测。

### S2B 组织管理与业务分析

徐介翰担任组长、项目经理兼技术经理，负责范围控制、系统研发、版本冻结和技术事实核验；孙竞杰建议担任产品经理，整理用户需求与使用流程；马星宇建议担任业务分析经理，提供制造场景、指标与成本假设；陈庚琦建议担任交互设计经理，负责操作路径和结果呈现；代洛瑞建议担任测试与交付经理，维护固定演示问题和验收记录。四位组员的岗位应在最终报告中按实际贡献确认。开发采用需求拆分、短周期实现、自动化与实机验收、问题回归、版本冻结的过程。三天初赛冲刺重点是统一材料和稳定展示，完整产品功能继续按后续里程碑交付。

### S2C 技术路线与实现方案

系统以 Python 与 FastAPI 构建服务端，以 React 与 TypeScript 构建交互界面，平台 PostgreSQL 保存业务元数据、会话和证据，Redis 与 Celery 承担任务队列，MinIO 保存较大的产物与报告。对企业 PostgreSQL 和 MySQL 数据源只读连接，先扫描和发布目录，再通过版本化语义模型把业务指标绑定到物理数据。Agent 通过模型网关调用 DeepSeek 等大模型完成自然语言理解、规划和回答，LangGraph 管理受控执行状态；工具注册层承载目录、查询、统计、图表和报告能力。查询由语义协议确定性编译，并经 SQLGlot、安全策略和只读限制验证。每轮运行保存计划、产物、验证和 Evidence，支持连续追问和断线恢复。完整路线继续增加隔离脚本执行、六类机器学习模型、黄金评测与运维观测。

### S2D 成本模型与可行性

成本由一次性适配成本和持续运行成本组成。一次性成本包括数据目录梳理、指标口径确认、语义映射、部署和培训；持续成本包括模型 API 调用、应用与 Worker 计算、平台数据库、对象存储、备份、安全与运维。建议按“月请求量 × 每次平均输入输出 Token × 模型单价”估算模型费用，按峰值并发和任务时长估算计算资源，按目录、证据、图表和报告保留期限估算存储。可提供企业私有化和托管服务两种交付模式，但实际价格、部署规格和客户需求需调研后填入。技术可行性由已运行的接入、语义、问析、图表和证据主链路支持；商业可行性则应通过试点客户、实测节省工时和复购需求验证，不能凭空写市场规模或收入预测。
