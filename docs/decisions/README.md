## 决策详情

### ADR-0001：首版聚焦质量分析

- 状态：已采纳
- 背景：官方覆盖生产、质量、设备和库存，全部同时实施会稀释产品深度。
- 决策：第一阶段完整实现质量分析，其他领域通过同一语义和工具协议后续扩展。
- 影响：样例数据、指标、评测和首轮交互围绕质量领域建设。

### ADR-0002：采用受控 Agent

- 状态：已采纳
- 背景：自由 ReAct 和多 Agent 讨论难以保证稳定性、安全和可复现性。
- 决策：使用持久化 Plan–Execute–Verify 状态机，每一步结构化、可验证、可恢复。
- 影响：Agent不是自由循环；所有循环必须有预算和退出条件。

### ADR-0003：能力与工具实现分离

- 状态：已采纳
- 背景：直接让模型在大量具体工具中选择，会增加错误率并绑定实现细节。
- 决策：Planner引用抽象能力，Tool Registry根据权限、版本和方言选择具体实现。
- 影响：工具可替换、可灰度、可按数据源适配。

### ADR-0004：双层语义数据架构

- 状态：已采纳
- 背景：企业表名和字段名差异大，不能将Agent写死到样例库。
- 决策：企业物理数据库映射到平台标准语义概念，映射和指标均版本化。
- 影响：数据接入需要管理员确认，换取查询正确性和可扩展性。

### ADR-0005：语义查询优先

- 状态：已采纳
- 背景：高性能模型仍可能产生业务口径正确但聚合方式错误的SQL。
- 决策：可信指标通过语义查询编译器生成SQL；仅探索性问题允许LLM生成SQL草案。
- 影响：答案界面区分可信语义查询和探索性查询。

### ADR-0006：Python后端与React前端

- 状态：已采纳
- 背景：项目同时需要Agent、SQL、统计建模和成熟企业工作台。
- 决策：Python 3.12/FastAPI负责后端，React/TypeScript/Vite负责前端。
- 影响：使用共享OpenAPI契约保持前后端一致。

### ADR-0007：有限使用LangGraph

- 状态：已采纳
- 背景：需要状态、分支、暂停和恢复，但不能把领域资产绑定到框架。
- 决策：LangGraph只承担编排；任务Schema、工具注册、权限、语义和验证自研。
- 影响：保留未来替换编排框架的能力。

### ADR-0008：DeepSeek经统一网关接入

- 状态：已采纳
- 背景：DeepSeek V4 Pro具备结构化输出、思考模式和工具调用能力，但供应商接口会演进。
- 决策：所有模型能力通过Model Gateway调用，业务代码禁止直接依赖供应商SDK。
- 影响：可以按任务配置推理模式、降级和备用模型。

### ADR-0009：基础设施基线

- 状态：已采纳
- 背景：需要事务数据、向量检索、缓存和异步任务，同时控制早期运维复杂度。
- 决策：PostgreSQL + pgvector保存平台数据，Redis + Celery承担缓存和异步任务。
- 影响：第一阶段不引入Kafka、Milvus和Temporal；达到明确规模条件后重新评估。

### ADR-0010：部署策略

- 状态：已采纳
- 背景：企业数据敏感，纯SaaS难以落地；比赛又需要便捷访问。
- 决策：Docker Compose私有化部署优先，使用脱敏样例数据提供公网演示。
- 影响：从第一阶段隔离控制面和数据执行职责，保留远程数据节点演进路径。

### ADR-0011：分析执行策略

- 状态：已采纳
- 背景：模型任意生成Python存在安全、稳定和复现风险。
- 决策：高频分析使用预注册确定性工具；高级代码在一次性受限容器中执行。
- 影响：沙箱默认无网络、无数据库凭证，并限制CPU、内存、时间和依赖。

### ADR-0012：答案发布要求

- 状态：已采纳
- 背景：查询成功不等于业务结论正确。
- 决策：答案必须通过结构、数据和语义验证，并绑定指标、SQL、结果和执行证据。
- 影响：验证失败进入修正、重新规划、澄清或明确失败，不输出伪确定性结论。

### ADR-0013：实施策略

- 状态：已采纳
- 背景：按组件横向开发容易长期无法形成真实闭环，也不利于Vibe Coding后的持续验收。
- 决策：按依赖顺序推进，每阶段形成可部署纵向增量并设置质量门禁。
- 影响：当前里程碑未验收前不堆叠下一阶段；任务必须同时具备实现、测试、文档和必要ADR。

### ADR-0014：M0运行时拓扑

- 状态：已采纳
- 背景：早期拆分大量微服务会增加部署、契约和调试成本，但后台任务与任意代码执行具有独立伸缩及安全边界。
- 决策：API采用模块化单体；异步任务使用独立Celery Worker；Sandbox保留独立服务边界并在M8完成受限实现。
- 影响：领域包保持无框架或低耦合，未来可按负载拆分；M0不在API进程内开放任意Python执行。

### ADR-0015：认证会话策略

- 状态：已采纳
- 背景：纯无状态长效JWT难以撤销，所有请求查询会话又会增加耦合和延迟。
- 决策：访问令牌使用15分钟HS256 JWT；刷新令牌使用高熵随机值，服务端只保存摘要并在每次刷新时轮换和撤销旧令牌。
- 影响：普通API可离线校验访问令牌；登出与刷新重放可受控；生产环境必须配置至少32字节随机密钥。

### ADR-0016：统一空间授权入口

- 状态：已采纳
- 背景：API、数据源和Agent工具分别实现权限判断容易产生绕过路径。
- 决策：授权请求统一表达主体、角色、动作和资源空间；跨空间默认拒绝，角色权限集中定义，路由只调用统一授权入口。
- 影响：后续工具注册表、查询执行器和导出模块必须复用相同Policy Engine；系统管理员角色只有系统管理员可以委派。

### ADR-0017：混合式工作台与前端会话边界

- 状态：已采纳
- 日期：2026-09-05
- 背景：产品既要突出自然语言问析，又必须承载数据源、语义模型、成员和审计等企业管理能力。
- 决策：首页以Agent问题输入为主操作，使用企业侧栏承载治理功能；访问令牌仅保存在内存，刷新流程集中在API Client，刷新令牌通过单一存储适配器管理。
- 备选方案：纯聊天界面、传统管理后台、浏览器内长期访问令牌。
- 选择理由：混合布局兼顾比赛表达与产品扩展；集中会话边界减少页面自行处理鉴权造成的竞态和泄漏面。
- 风险：首版刷新令牌适配器使用`localStorage`，需要严格控制XSS，并在具备同源BFF部署条件后迁移为`HttpOnly`、`Secure`、`SameSite` Cookie。
- 后续影响：业务页面不得直接读取令牌；所有受保护请求经过共享API Client；导航能力以真实后端就绪状态逐步开放。
- 重新评估条件：引入同源网关、SSO/OIDC或多端客户端时重新设计刷新凭据承载方式。

### ADR-0018：数据源信封加密与网络策略前置

- 状态：已采纳
- 日期：2026-09-05
- 背景：数据源凭据和内网连接能力属于高风险资产；单纯数据库字段加密无法提供资源绑定、密钥轮换和SSRF/DNS重绑定防护。
- 决策：每个数据源使用独立随机数据密钥，以AES-256-GCM加密凭据；主密钥只包装数据密钥，AAD绑定工作空间和数据源。任何连接在建立前必须完成端口、DNS结果、地址类别和私网CIDR策略校验，连接后再次核对实际目标地址。
- 备选方案：明文或应用级固定密钥加密、数据库透明加密、仅校验用户输入主机名、直接依赖云密钥服务。
- 选择理由：信封加密兼顾本地私有化部署和未来KMS接入，可在不解密凭据正文的情况下轮换主密钥；双阶段地址校验覆盖常见SSRF和DNS重绑定路径。
- 风险：私网数据源必须显式配置CIDR；主密钥遗失会导致凭据不可恢复；驱动层仍需确保实际连接地址可被复核。
- 后续影响：API、日志和任务载荷不得返回密文或明文凭据；连接器必须复用Secret Provider与Network Policy，不得自行旁路；生产环境禁止开发主密钥。
- 重新评估条件：接入云KMS/HSM、远程数据节点或企业密钥托管要求时替换主密钥包装适配器，保持密文格式版本兼容。

### ADR-0019：Connector协议与事务Outbox

- 状态：已采纳
- 日期：2026-09-05
- 背景：连接测试涉及外部网络、凭据和不可控延迟，不能占用API请求线程；直接在数据库提交后发送Celery消息又存在提交成功但消息丢失窗口。
- 决策：API事务同时写入数据源、任务和Outbox事件；独立Celery Beat触发发布器，发布器只把任务ID送入队列；Worker临时解密并通过Connector协议执行连接、TLS和只读验证。
- 备选方案：API同步连接、提交后直接调用Celery、数据库触发器、早期引入Kafka或Temporal。
- 选择理由：事务Outbox消除主要双写窗口，现有PostgreSQL与Celery即可实现；Connector将数据库方言隔离，后续MySQL无需改动控制面。
- 风险：发布操作具备至少一次语义，任务实现必须幂等；Celery Beat当前是单实例调度器，生产部署需保证同一计划只有一个活动实例。
- 后续影响：任务消息不得携带凭据；Worker必须按任务状态短路重复投递；扫描、采样和后续长任务继续复用同一Outbox模式。
- 重新评估条件：跨地域节点、百万级事件积压或需要长事务编排时评估专用Outbox relay、Kafka或Temporal。

### ADR-0020：不可变规范化目录与确定性差异

- 状态：已采纳
- 日期：2026-09-05
- 背景：Agent、语义模型和前端需要稳定理解企业数据库结构，同时不能依赖PostgreSQL系统表细节，也不能让失败扫描污染上一成功版本。
- 决策：连接器输出方言无关的`MetadataDocument`；平台将Schema、关系、字段、约束和索引写入带快照作用域的规范化表。每次成功扫描发布不可变递增版本，使用规范JSON的SHA-256摘要和稳定对象键计算相邻版本差异；模型不参与结构差异判断。
- 备选方案：只保存系统表原始JSON、原地覆盖当前目录、依赖LLM判断结构变化、引入外部数据目录产品。
- 选择理由：规范化目录便于空间隔离、版本查询和后续语义建模；确定性算法可测试、可复现、成本稳定；构建中/发布/拒绝状态使原子发布和失败恢复清晰。
- 风险：大型数据库会产生较多目录行；首版单次扫描对象数受`METADATA_SCAN_MAX_OBJECTS`限制，目录读取目前以单快照完整树返回。
- 后续影响：MySQL连接器必须生成相同文档契约；Agent工具只读取已发布快照；采样画像必须绑定具体快照，不能修改历史目录。
- 重新评估条件：单源对象规模超过十万、需要跨区域目录同步或外部血缘治理时，评估分段扫描、对象存储归档与专业目录集成。

### ADR-0021：MySQL原生连接器与单库边界

- 状态：已采纳
- 日期：2026-09-05
- 背景：平台需要在不污染控制面和目录模型的前提下支持MySQL，并保持DNS重绑定、TLS、只读权限、超时和版本差异等安全能力。
- 决策：使用纯Python的PyMySQL实现独立Connector；先连接网络策略已授权的固定IP，同时保留配置主机名用于TLS SNI与身份校验。MySQL的database映射为一个目录Schema，默认及显式扫描均不得扩张到其他数据库。
- 备选方案：SQLAlchemy Inspector、依赖系统动态库的mysqlclient、允许扫描账户可见的全部数据库。
- 选择理由：原生系统表查询可精确控制字段、约束、索引和错误映射；PyMySQL部署链路简单，适合Windows开发与Linux容器；单库边界符合数据源配置语义并减少越权发现面。
- 风险：MySQL与PostgreSQL原生类型和默认表达式并不完全等价；PyMySQL的预连接socket注入需要随驱动升级做回归验证；大型单库仍受对象总量上限约束；启用MySQL角色的账户在角色权限展开实现前会被默认拒绝。
- 后续影响：新数据库连接器必须继续输出`MetadataDocument`并通过跨方言契约测试；升级PyMySQL时必须复测TLS握手、固定地址连接和底层socket关闭行为。
- 重新评估条件：需要企业MySQL角色展开、多数据库统一数据源或远程数据节点时，扩展权限解析与扫描作用域模型，不在连接器中隐式放宽。

### ADR-0022：元数据发布与画像任务解耦

- 状态：已采纳
- 日期：2026-09-05
- 背景：安全画像需要读取有限业务数据，失败概率和资源消耗高于元数据扫描；若二者共用一个发布事务，画像超时会阻塞本来可用的结构目录。
- 决策：元数据快照先独立发布，再根据默认关闭的采样策略创建绑定该快照的`profile_scan`任务。画像状态和结果属于快照附属数据，但失败、取消或重试不改变已发布目录实体。
- 备选方案：元数据与画像在同一任务中原子发布、仅使用数据库统计表、不保存任何有限样例。
- 选择理由：两阶段模型保留目录可用性，并使画像拥有独立的授权、预算、取消、错误与重试边界；快照绑定仍能保证可追溯性。
- 风险：快照可能短暂或永久处于画像待处理/失败状态；控制面和前端必须明确区分目录状态与画像状态。
- 后续影响：画像任务必须使用冻结预算并保持幂等；Agent只能读取画像成功或明确允许的聚合结果；敏感字段永不保存原值。
- 重新评估条件：需要跨源一致画像、超大规模分布式采样或专业数据目录集成时，评估工作流引擎与分片画像，但不放宽授权和预算边界。

### ADR-0023：确定性敏感识别与多层硬预算

- 状态：已采纳
- 日期：2026-09-05
- 背景：画像需要有限读取业务值，但不能依赖模型是否正确判断敏感信息，也不能让单一SQL行数限制成为唯一资源边界。
- 决策：字段名、数据库类型和有限值使用确定性规则联合识别，身份证与银行卡执行校验算法；任何识别异常均失败关闭。连接器、统一画像引擎和数据库约束共同执行行数、值数、字符数、表级字节、任务字节和超时预算。
- 备选方案：让LLM判定敏感字段、只按字段名过滤、只限制SQL的`LIMIT`、完全不保存任何脱敏样例。
- 选择理由：确定性规则可测试、可解释且不受模型漂移影响；多层预算能覆盖驱动异常、连接器实现错误和UTF-8长度差异，同时保留普通字段的有限产品价值。
- 风险：规则可能保守地阻止部分普通字段，新增国家证件或行业标识需要扩展识别器。
- 后续影响：Agent只能消费已持久化的安全画像；任何新增连接器必须复用统一画像引擎并通过原值零泄漏测试。
- 重新评估条件：新增国家/行业敏感类型或引入企业DLP服务时，可扩充识别来源，但不得改为仅依赖LLM。

### ADR-0024：数据库状态驱动的计划领取与任务恢复

- 状态：已采纳
- 日期：2026-09-05
- 背景：Celery消息采用至少一次投递，单靠定时器内存或Broker状态无法保证计划槽幂等、Worker失联恢复和显式重试可追溯。
- 决策：计划、下次执行时间、任务状态、心跳、尝试次数和幂等键均以PostgreSQL为事实源；到期计划使用行锁领取，事务Outbox投递，失联任务最多恢复两次，显式重试创建带来源链路的新任务。
- 备选方案：仅使用Celery Beat静态配置、直接从API发送Celery消息、无限自动重试、在原任务上清空终态后重跑。
- 选择理由：数据库事务同时保护业务状态与待投递事件；计划槽键、终态短路和新任务重试链使重复消息与人工操作均可审计。
- 风险：生产环境必须保证单一活动Beat实例，并为长任务设置与心跳频率匹配的失联阈值。
- 后续影响：新异步任务需要注册Outbox事件、终态短路和恢复规则；分布式扩展时仍以数据库租约或等价持久化协调为准。
- 重新评估条件：任务规模需要分片调度或跨区域执行时，评估工作流引擎，但保留幂等、Outbox与审计语义。

### ADR-0025：前端服务器状态与短生命周期凭据

- 状态：已采纳
- 日期：2026-09-06
- 背景：数据源创建、连接检测、扫描和画像均为异步服务器状态，后续页面需要一致的缓存、轮询、失效和错误恢复；数据库凭据又不能进入长期客户端状态。
- 决策：引入TanStack Query管理数据源及任务服务器状态，认证继续由AuthProvider负责；接入向导使用React Hook Form和Zod管理短生命周期输入，提交完成后立即清空密码字段，不把凭据写入Query缓存、Context、本地存储或URL。
- 备选方案：每个页面自行使用`useEffect`和`useState`请求、将表单状态放入全局Store、一次性引入完整前端状态框架。
- 选择理由：TanStack Query提供成熟的请求去重、缓存失效和条件轮询，适合后续目录与Agent任务；把秘密留在局部表单可缩小泄漏面，且不需要引入无关的客户端全局状态。
- 风险：服务器状态键和失效规则需要统一维护；长页面必须控制轮询频率和页面后台行为；开发工具不得展示或持久化请求秘密。
- 后续影响：目录、画像和Agent任务沿用分层Query Key与终态失效模式；任何凭据轮换界面必须遵守同一短生命周期约束。
- 重新评估条件：需要离线优先、大规模实时协同或跨标签页任务同步时，再评估持久化缓存与推送机制，但秘密字段仍不得持久化。
### ADR-0026：规范语义文档快照与不可变发布版本

- 状态：已采纳
- 日期：2026-09-07
- 背景：Agent、查询编译器和审计需要在一次运行中引用完全一致的实体、指标、公式与映射，规范化多表原地编辑容易产生中间不一致与版本漂移。
- 决策：逻辑模型保存管理状态，版本表保存经严格契约校验的完整规范JSON、对象计数与SHA-256摘要；草稿使用乐观锁，发布后不可原地修改。
- 备选方案：实体/维度/指标分别建表并原地更新、仅保存YAML文件、每次执行读取最新配置。
- 选择理由：单文档快照可原子发布、稳定摘要、便于Agent和M4编译器缓存，也让历史证据能够精确绑定版本。
- 风险：大型模型的局部编辑需要整体校验与写入；后续若单模型超过当前规模，应增加差量编辑协议但仍生成完整发布快照。
- 后续影响：所有Agent运行只能消费已发布版本ID与摘要；新公式类型必须先扩展契约、验证器和编译器。

### ADR-0027：确定性映射候选与人工确认

- 状态：已采纳
- 日期：2026-09-07
- 背景：大模型适合解释候选，但不能凭空创建物理字段或绕过目录与空间边界。
- 决策：候选集合来自当前工作空间的真实目录快照，使用确定性名称匹配产生置信度与理由；模型后续只能在候选内排序或补充解释，管理员确认后写入，发布时再次校验快照、关系、字段归属与确认状态。
- 备选方案：让模型直接输出表字段名、自动接受最高分候选、由前端单独保存映射。
- 选择理由：把模型的不确定性限制在建议层，后端保持可验证的对象ID链路，为后续工具选择和SQL编译提供可信输入。
- 风险：缩写或中文字段的纯规则召回率有限；低召回时需要人工选择或受控模型重排，不能降低归属校验。
- 后续影响：M4只编译已确认映射；M5的模型工具不得接受目录外自由字段。
### ADR-0028：编译优先、统一AST门禁与验证ID能力票据

- 状态：已采纳
- 日期：2026-09-07
- 背景：高性能模型仍可能生成口径漂移、越权或资源不可控的SQL；仅在提示词中要求只读无法形成安全边界。
- 决策：常规分析由已发布语义版本确定性编译参数化SQL，探索SQL也必须通过同一SQLGlot AST与目录对象白名单；执行器拒绝原始SQL，只接受短时、工作空间绑定、目录版本绑定的持久化验证ID。
- 备选方案：模型直接调用数据库、只用正则检查SQL、API在一次请求中校验后立即执行、为可信与探索查询各做一套安全器。
- 选择理由：编译路径稳定业务口径，统一AST门禁避免规则分叉，验证ID把“校验成功”转化为可过期且可审计的能力票据，并允许执行前再次检查快照漂移。
- 风险：验证与执行之间仍需控制有效期和目录变更；复杂查询能力必须显式扩展协议；同步短查询执行未来在高并发下需要迁移到Worker状态机。
- 后续影响：M5 Agent只能调用编译、验证和ID执行工具，不得把模型SQL直接送入连接器；答案证据必须引用验证ID、语义版本、目录快照和结果摘要。
- 重新评估条件：引入远程数据执行节点、长查询、查询队列或细粒度行级策略时，扩展能力票据声明与异步执行状态，但不取消统一安全门禁。

### ADR-0030：执行时追问分类与白名单跨轮上下文

- 状态：已采纳
- 日期：2026-09-16
- 背景：连续会话已经允许同一任务发送多轮消息，但如果新轮独立理解，会丢失旧指标；如果直接把完整运行上下文传给模型，又会继承 SQL、错误、敏感数据或过期结果。排队消息还可能在等待期间遇到上下文变化。
- 决策：每个 Turn 保持独立 AnalysisRun；追问在真正执行时基于最新稳定轮分类。高频表达由确定性规则处理，其他表达通过严格 FollowUpDecision 回退到 Model Gateway。显式时间追问的确定性补丁在模型修订后再次应用，粒度词只可解析为当前指标唯一支持的时间维度，并由计划显式传入 `time_grain`。跨轮只传递受 Pydantic 限制的业务上下文和已验证 Artifact/Evidence 引用，Intent 修订仍经过本地绑定、权限、Planner 与工具注册表。解释类追问调用 analysis.describe 引用旧证据，不重新查询；换题清除冲突上下文。
- 备选方案：把完整聊天记录直接交给模型、排队时立即冻结上下文、复用并重开已完成 AnalysisRun、每轮完全独立理解。
- 选择理由：执行时分类避免排队状态陈旧；白名单上下文兼顾多轮体验和最小披露；独立 Run 保持预算、证据和审计不可变；确定性优先降低延迟与模型不稳定性。
- 风险：未知表达可能额外消耗一次分类调用；非显式自然时间范围仍由 IntentRevision 解析；指标没有唯一兼容时间维度时必须澄清或受控失败，不能猜测；会话上下文投影字段扩展必须保持 16 KiB 上限和显式版本。
- 后续影响：非业务寒暄使用受控 small_talk Intent 和内部系统回答，不继承为后续业务 Intent，也不覆盖原分析上下文；M7.3 恢复扫描必须在激活排队轮时刷新 context_before；M7.5 推荐追问也必须作为普通消息重新分类和鉴权；M7.6 图表只能引用已验证 Artifact。
- 重新评估条件：模型提供可证明的原生状态对象或会话上下文超过单主题边界时，可以扩展版本化契约，但不得传递原始 SQL、凭据或内部推理。

## ADR-016：Agent 采用确定性控制面与 DeepSeek 受控决策

- 日期：2026-09-08
- 状态：接受
- 决策：使用供应商无关 Model Gateway 对接 DeepSeek 官方 Chat Completions；LangGraph 只负责有界节点拓扑，运行、预算、计划、检查点和证据由平台数据库持久化。模型只产出意图候选和声明式计划，所有绑定、权限、指标口径、SQL 安全与执行均由确定性系统裁决。
- 原因：模型自由工具循环无法保证权限、幂等、恢复和证据一致性；完全自研图运行时会增加无业务收益的维护成本。
- 后续影响：M6 复用 analysis_events 提供 SSE；M7 在不改变 Planner 契约的前提下实现分析、图表和报告工具。

### ADR-0029：持久化运行投影、可重放事件与严格结构化模型输出

- 状态：已采纳
- 日期：2026-09-09
- 背景：正式问析界面必须支持刷新恢复、断线续传、人工确认和证据定位；模型的 JSON 模式只能保证语法，不能保证业务契约完整。
- 决策：PostgreSQL 中的 AnalysisRun 聚合是唯一事实源，SSE 只传递带单调序号的增量通知；前端用服务端完整投影建立基线并在关键事件或序号空洞时重新取权威状态。DeepSeek 结构化请求显式携带 Pydantic JSON Schema，响应仍由严格契约验证；首次不合格只允许一次携带精简验证错误的纠正，并累计全部调用与 Token。
- 备选方案：仅依赖进程内 WebSocket 状态、把 SSE 当事实源、浏览器自行推断最终结果、放宽 Pydantic 字段、无限要求模型重试。
- 选择理由：持久化投影和可重放事件使恢复不依赖单机内存；严格 Schema 加有界纠正提高模型适配率，同时不牺牲确定性边界、预算和审计准确性。
- 风险：关键事件会额外触发一次投影读取；模型纠正会增加一次调用成本；事件契约升级必须保持旧客户端可忽略未知类型。
- 后续影响：M7 的统计、图表和报告产物继续写入 Artifact/Evidence/Validation，不在前端复制业务计算；新增结构化模型任务必须复用同一 Schema 与有界纠正规则。
- 重新评估条件：引入原生严格 JSON Schema 响应接口、跨区域事件总线或百万级并发运行时，可替换传输实现，但事实源、预算和严格验证语义保持不变。
