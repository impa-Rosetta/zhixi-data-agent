## 决策详情

### ADR-0001：首版聚焦质量分析

- 状态：已采纳
- 背景：官方覆盖生产、质量、设备和库存，全部同时实施会稀释产品深度。
- 决策：第一阶段完整实现质量分析，其他领域通过同一语义和工具协议后续扩展。
- 影响：样例数据、指标、评测和首轮交互围绕质量领域建设。

### ADR-0002：采用受控 Agent

- 状态：已采纳
- 背景：自由 ReAct 和多 Agent 讨论难以保证稳定性、安全和可复现性。
- 决策：使用持久化 Plan–Execute–Verify 状态机，每一步结构化、可验证、可恢复。
- 影响：Agent不是自由循环；所有循环必须有预算和退出条件。

### ADR-0003：能力与工具实现分离

- 状态：已采纳
- 背景：直接让模型在大量具体工具中选择，会增加错误率并绑定实现细节。
- 决策：Planner引用抽象能力，Tool Registry根据权限、版本和方言选择具体实现。
- 影响：工具可替换、可灰度、可按数据源适配。

### ADR-0004：双层语义数据架构

- 状态：已采纳
- 背景：企业表名和字段名差异大，不能将Agent写死到样例库。
- 决策：企业物理数据库映射到平台标准语义概念，映射和指标均版本化。
- 影响：数据接入需要管理员确认，换取查询正确性和可扩展性。

### ADR-0005：语义查询优先

- 状态：已采纳
- 背景：高性能模型仍可能产生业务口径正确但聚合方式错误的SQL。
- 决策：可信指标通过语义查询编译器生成SQL；仅探索性问题允许LLM生成SQL草案。
- 影响：答案界面区分可信语义查询和探索性查询。

### ADR-0006：Python后端与React前端

- 状态：已采纳
- 背景：项目同时需要Agent、SQL、统计建模和成熟企业工作台。
- 决策：Python 3.12/FastAPI负责后端，React/TypeScript/Vite负责前端。
- 影响：使用共享OpenAPI契约保持前后端一致。

### ADR-0007：有限使用LangGraph

- 状态：已采纳
- 背景：需要状态、分支、暂停和恢复，但不能把领域资产绑定到框架。
- 决策：LangGraph只承担编排；任务Schema、工具注册、权限、语义和验证自研。
- 影响：保留未来替换编排框架的能力。

### ADR-0008：DeepSeek经统一网关接入

- 状态：已采纳
- 背景：DeepSeek V4 Pro具备结构化输出、思考模式和工具调用能力，但供应商接口会演进。
- 决策：所有模型能力通过Model Gateway调用，业务代码禁止直接依赖供应商SDK。
- 影响：可以按任务配置推理模式、降级和备用模型。

### ADR-0009：基础设施基线

- 状态：已采纳
- 背景：需要事务数据、向量检索、缓存和异步任务，同时控制早期运维复杂度。
- 决策：PostgreSQL + pgvector保存平台数据，Redis + Celery承担缓存和异步任务。
- 影响：第一阶段不引入Kafka、Milvus和Temporal；达到明确规模条件后重新评估。

### ADR-0010：部署策略

- 状态：已采纳
- 背景：企业数据敏感，纯SaaS难以落地；比赛又需要便捷访问。
- 决策：Docker Compose私有化部署优先，使用脱敏样例数据提供公网演示。
- 影响：从第一阶段隔离控制面和数据执行职责，保留远程数据节点演进路径。

### ADR-0011：分析执行策略

- 状态：已采纳
- 背景：模型任意生成Python存在安全、稳定和复现风险。
- 决策：高频分析使用预注册确定性工具；高级代码在一次性受限容器中执行。
- 影响：沙箱默认无网络、无数据库凭证，并限制CPU、内存、时间和依赖。

### ADR-0012：答案发布要求

- 状态：已采纳
- 背景：查询成功不等于业务结论正确。
- 决策：答案必须通过结构、数据和语义验证，并绑定指标、SQL、结果和执行证据。
- 影响：验证失败进入修正、重新规划、澄清或明确失败，不输出伪确定性结论。
