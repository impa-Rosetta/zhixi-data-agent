# M6.2 自然语言会话呈现层设计

## 1. 背景与目标

当前分析流程已经能够保存澄清请求、权限判定、失败代码、证据和校验结果，但部分机器状态被直接展示给最终用户，例如 `agent.clarification_required`、独立的“Agent 需要你补充信息”表单，以及偏技术化的权限或执行错误。这会让普通用户误以为 Agent 无法交流，也破坏了连续对话体验。

本阶段新增“自然语言会话呈现层”：Agent 在成功、需要补充信息、权限不足、数据条件不足、超出能力范围或发生临时故障时，都应以自然语言直接回复用户；结构化状态继续作为流程控制和审计依据，但不再作为主要用户界面。

## 2. 设计原则

1. **对话优先**：主界面始终以用户消息和 Agent 消息组成连续会话。
2. **结构化控制**：澄清、权限、错误、证据和验证仍使用结构化对象驱动，不依赖自然语言反解析。
3. **事实确定性**：权限事实、资源存在性、失败原因和可执行操作由后端确定性映射，不能交给大模型猜测。
4. **安全最小披露**：无权访问时不得透露隐藏资源名称、数量、结构或其他租户信息。
5. **可恢复**：澄清和可重试错误必须保留继续执行所需的检查点。
6. **技术细节降级**：内部错误码只出现在审计面板或可展开的技术详情中。

## 3. 总体架构

```text
用户问题
  -> Agent 规划与工具调用
  -> 结构化运行结果
       - completed
       - clarification_required
       - permission_denied
       - data_not_ready
       - unsupported
       - transient_failure
  -> 会话呈现层（安全、确定性）
  -> Agent 自然语言消息 + 可选快捷回复/操作
  -> Web 对话界面
```

会话呈现层不取代现有 Agent Runtime、Policy Engine 或查询执行器，只负责把已经确定的事实组织成安全、清晰、可操作的用户消息。

## 4. 统一响应契约

后端对每次可见状态生成统一的会话响应：

```json
{
  "message": {
    "role": "assistant",
    "content": "你想查看哪个时间范围的不良率？",
    "tone": "neutral"
  },
  "interaction": {
    "kind": "clarification",
    "quick_replies": ["最近一周", "最近一个月", "全部数据"],
    "retryable": false
  },
  "technical": {
    "code": "agent.clarification_required",
    "visible_in_inspector": true
  }
}
```

其中 `message.content` 是面向用户的主要内容；`interaction` 描述快捷回复、重试或其他安全操作；`technical` 只供审计和诊断界面使用。现有结构化 clarification、evidence、validation 等对象继续保留，避免破坏运行恢复能力。

## 5. 各类状态的自然语言行为

### 5.1 需要补充信息

- Agent 在对话气泡内提出一个明确问题。
- 说明缺少的是指标、时间范围、分析对象还是分组维度。
- 建议值以快捷回复展示，用户也可以自由输入。
- 用户回复后从当前检查点继续，不创建割裂的新分析。
- 页面不再将“Agent 需要你补充信息”作为主要表单标题，也不直接展示 `agent.clarification_required`。

示例：

> 我可以帮你分析整体质量。为了得到准确结果，你更关注不良率、一次通过率，还是检验合格率？

### 5.2 权限不足

- 使用通用资源描述，避免确认用户无权获知的资源是否存在。
- 明确当前操作没有执行，不伪装成无数据。
- 提供安全的下一步，例如选择已授权数据或联系管理员。
- 不显示策略规则、内部角色标识或原始异常堆栈。

示例：

> 当前账号没有执行这项分析所需的数据访问权限。我没有读取相关数据。你可以改用已授权的数据范围，或联系工作区管理员申请权限。

### 5.3 数据或语义条件不足

- 区分“没有数据”和“缺少计算所需字段/映射”。
- 如果已经识别指标，应告诉用户目前缺少哪类业务信息，但不暴露不必要的内部表结构。
- 提供当前数据能够完成的替代分析。

示例：

> 我识别到你想计算一次通过率，但当前发布的数据模型还没有提供一次通过数量，因此暂时无法可靠计算。现在可以先分析不良率或检验数量趋势。

### 5.4 超出能力范围

- 礼貌说明产品能力边界。
- 给出 2～3 个可执行的问题示例。
- 保留明确的终止状态，但用户看到的是正常 Agent 回复，不是红色系统错误。

### 5.5 临时故障

- 告诉用户本次分析未完成、是否执行过数据操作以及能否重试。
- 提供重试按钮或调整问题的建议。
- 原始供应商错误、网络地址、密钥信息和堆栈不得进入用户消息。

## 6. 内容生成策略

采用“确定性事实模板 + 可选语言润色”的组合：

- 第一阶段全部使用后端模板与安全字段生成，确保可测试、低延迟、无模型幻觉。
- 正常数据分析结果仍由 DeepSeek 结合工具结果生成自然语言回答。
- 后续如需提高语气自然度，可以让模型仅润色已经生成的安全内容；润色失败时必须回退到确定性模板。
- 模型永远不能修改权限结论、资源范围、错误分类和允许执行的操作。

## 7. 前端交互

- 所有状态首先渲染为 Agent 消息气泡。
- 澄清建议显示为消息下方的快捷回复按钮。
- 自由输入框保持可用，用户无需必须点击建议项。
- 可重试故障显示“重新尝试”操作。
- 原始状态码从主对话移除，迁移到审计/技术详情。
- 状态标签可保留，但改用“等待你的回答”“权限受限”“暂时无法计算”等用户语言。
- 桌面端和移动端保持一致的会话语义。

## 8. 持久化与恢复

- 自然语言回复作为 `assistant` 角色消息持久化，刷新页面后仍可见。
- 结构化交互元数据与消息关联，供快捷回复、重试和流程恢复使用。
- 用户补充内容作为新的 `user` 消息写入，并引用待处理的澄清请求。
- 重复提交采用幂等键，避免一次回复触发两次运行。
- 历史运行继续兼容：如果旧记录没有自然语言消息，前端使用同一套安全映射生成回退文案。

## 9. 安全边界

- 仅允许经过白名单的业务名称、指标名称和时间范围进入模板。
- 禁止展示 API Key、连接串、SQL 原文中的敏感值、异常堆栈和模型内部推理。
- 权限失败响应不引用未经授权的具体对象。
- 技术错误详情仍受工作区角色权限控制。
- 所有用户可见内容经过敏感信息回归测试。

## 10. 实施切片

1. 后端定义统一会话响应类型和错误分类映射。
2. Runtime 在澄清、数据条件不足、能力边界和临时故障路径生成并持久化 Agent 消息。
3. Policy/API 权限错误接入安全自然语言响应。
4. Web 统一渲染 Agent 气泡、快捷回复、重试和折叠技术详情。
5. 为旧运行记录增加兼容回退。
6. 扩展真实问题矩阵及桌面/移动端端到端测试。

## 11. 验收标准

- “整体质量怎么样”由 Agent 主动追问指标，并可通过自由输入或快捷回复继续。
- “一次通过率是多少”在数据模型不完整时得到明确、自然且可行动的解释，而不是 `agent.execution_failed`。
- 未授权请求不显示内部错误码或隐藏资源信息。
- 超出范围的问题收到能力边界说明和可执行示例。
- 临时模型故障收到可重试说明，且不会泄露供应商原始错误。
- 刷新页面后 Agent 自然语言消息、快捷回复和运行状态保持一致。
- 主对话中不出现 `agent.*`、堆栈或其他内部代码。
- 后端单元/契约测试、前端组件测试以及桌面与移动端 E2E 全部通过。

## 12. 非目标

- 本阶段不让大模型自行判断权限。
- 本阶段不删除结构化错误、证据或审计数据。
- 本阶段不通过提示词掩盖缺失的数据字段或语义映射。
- 本阶段不把所有失败伪装成成功；运行状态仍保持真实，只改变用户沟通方式。
