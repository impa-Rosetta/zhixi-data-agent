# M6 智能问析工作台设计规格

- 状态：已批准，待实施
- 日期：2026-09-08
- 上游能力：M5 Agent 核心、M4 安全查询内核、M3 语义模型
- 阶段边界：M6 交付实时任务工作台与结果证据；高级图表、统计分析和报告归入 M7

## 1. 目标与完成定义

M6 将现有 AnalysisRun 后端闭环交付为可实际使用的企业问析工作台。用户能够发起自然语言分析、观察真实执行过程、处理澄清和计划确认、取消或重试任务，并在刷新或短时断网后恢复到同一运行状态。完成的结果必须展示真实查询产物、验证结论和可定位证据，不允许前端生成模拟答案或用固定数据替代后端结果。

M6 完成需同时满足：

1. 用户仅通过 Web 可完成创建、跟踪、澄清、确认、取消、重试和查看历史任务；
2. 事件使用可重放 SSE 协议传输，断线后从最后已确认序号续传且不重复应用；
3. 页面刷新后可从服务端投影恢复消息、状态、计划、步骤、产物、证据和验证记录；
4. 每个展示的最终数字能关联到产物、查询、冻结版本和验证记录；
5. 密钥、凭据、完整模型思考内容和未脱敏样例不会进入接口、事件、日志或浏览器状态；
6. 后端、前端、真实浏览器、迁移与 Compose 验收全部通过并对应同一 Git 提交。

## 2. 方案选择

采用“数据库事件日志 + HTTP 投影接口 + Fetch SSE 客户端”的方案。

- 不采用定时轮询作为主通道，因为它不满足正式实时事件流和断线续传目标；
- 不采用 WebSocket，因为当前数据主要由服务端单向输出，双向长连接会增加鉴权、重连和部署复杂度；
- 不使用原生 `EventSource`，因为现有前端使用 Bearer Token，原生接口无法可靠附加 Authorization 请求头；
- 使用 `fetch` 读取 `text/event-stream`，复用现有令牌刷新策略并自行维护最后事件序号。

PostgreSQL 中的 `analysis_events` 是唯一事件事实源。SSE 连接先重放指定序号之后的持久化事件，再以短间隔读取新增事件并发送心跳。首版不增加 Redis Pub/Sub 作为正确性依赖；后续可用通知机制降低尾延迟，但任何通知丢失都不影响事件恢复。

## 3. 产品信息架构

桌面端采用三栏布局：

1. 左栏“分析任务”：创建入口、任务历史、状态、更新时间和恢复入口；
2. 中栏“对话与结果”：问题、多轮消息、运行状态、进度、澄清输入、计划确认、取消重试和最终结果；
3. 右栏“执行与证据”：计划步骤、工具调用、验证、可信等级、警告、Evidence 定位和可展开技术详情。

窄屏按任务列表、对话结果、执行证据三个可切换视图呈现；任何核心操作不得只存在于 hover 或宽屏侧栏。业务默认视图隐藏 SQL、模型、工具版本和内部错误详情，用户主动展开后才显示已脱敏技术信息。

状态对应行为如下：

| 状态 | 主界面行为 | 可用操作 |
| --- | --- | --- |
| `queued` / `running` | 显示当前节点、进度事件和预算摘要 | 取消 |
| `waiting_for_clarification` | 显示澄清原因与输入框 | 补充消息 |
| `waiting_for_confirmation` | 显示只读计划、风险和预算 | 批准、拒绝 |
| `completed` | 展示结果、验证、证据和技术详情 | 发起后续问题 |
| `failed_retryable` | 保留已完成产物并显示可行动错误 | 重试 |
| `failed` | 保留证据并显示终态原因 | 新建分析 |
| `cancelled` | 显示取消位置和已保留产物 | 新建分析 |

## 4. 后端接口与投影

保留 M5 已有创建、详情、消息、确认、取消、重试和历史事件接口，并新增：

- `GET /api/v1/workspaces/{workspace_id}/analysis-runs`：按更新时间倒序分页返回运行摘要；
- `GET /api/v1/workspaces/{workspace_id}/analysis-runs/{run_id}/view`：返回工作台恢复所需的完整只读投影；
- `GET /api/v1/workspaces/{workspace_id}/analysis-runs/{run_id}/events/stream`：SSE 重放和实时事件流。

运行摘要只包含列表所需字段。完整投影包含 `run`、消息、当前计划、步骤、工具调用摘要、产物、证据和验证，不返回活动检查点中的受限推理状态。所有查询以 `workspace_id` 和当前用户授权为边界。

SSE 协议约定：

- 事件 `id` 等于持久化的递增 `sequence`；
- `event` 等于受控 `event_type`；
- `data` 是与现有 `AnalysisEventResponse` 一致的 JSON；
- 客户端通过 `Last-Event-ID` 请求头恢复，也可使用 `after` 查询参数作为浏览器兼容后备；
- 服务端在无新事件时发送注释心跳，终态事件发送完成后正常关闭；
- 单次批量重放有上限，超过上限时分批发送而不是跳过事件；
- 客户端按 `sequence` 去重，发现序号空洞时重新拉取 HTTP 投影和缺失事件。

## 5. 前端模块边界

新增 `features/analysisRuns`，内部按职责拆分：

- API 层：运行 CRUD、投影读取和 SSE 流解析；
- Store/Hook 层：以服务端投影为基线，按事件序号归并增量状态；
- Run List：分页历史、状态筛选和选中任务；
- Conversation：消息、问题输入、澄清与多轮上下文；
- Run Controls：确认、拒绝、取消和重试；
- Execution Timeline：节点、计划步骤和工具调用状态；
- Result View：指标卡、通用表格、可信等级与警告；
- Evidence Drawer：数字到 Evidence、查询、冻结版本和验证的定位；
- Technical Details：按需展示已脱敏的 SQL、工具和模型元数据。

组件只消费稳定前端类型，不直接解释任意事件 payload。事件归并器是唯一把后端事件转换成界面状态的位置，未知事件保留在技术时间线但不得破坏页面。

## 6. 数据流与恢复

创建任务时，客户端生成一次性幂等键并提交问题。收到运行对象后立即导航到该任务、获取完整投影并连接 SSE。

正常事件流：

```text
创建/恢复 AnalysisRun
→ 获取服务端完整投影和最后事件序号
→ 以最后序号连接 Fetch SSE
→ 按序去重并归并事件
→ 关键状态变化重新校准投影
→ 终态事件后完成最终投影读取并关闭连接
```

页面刷新时 URL 保留 `run_id`。客户端先恢复投影再连接事件流，不依赖内存中的旧消息。网络中断采用带抖动的指数退避；401 先执行一次现有令牌刷新，仍失败则回到登录页；连续失败不清空已加载结果。

用户操作均采用服务端响应覆盖本地状态。确认、补充消息和重试成功后使用返回的运行版本重新连接事件流，避免本地猜测状态机迁移。

## 7. 结果、可信度与证据

M6 只展示 M5/M4 已持久化的真实产物，不在浏览器重新计算业务指标。结果渲染支持：

- 单值与少量指标卡；
- 字段已知的通用数据表格；
- 空结果、截断结果和部分完成状态；
- 验证通过、带警告和失败三类可信状态；
- 数据快照、语义版本、指标版本、查询 ID、工具调用和校验记录引用。

Evidence 采用稳定标识引用，不把大结果复制进事件流。点击结果中的证据标记后，在右栏定位对应 Evidence，并显示来源、时间、校验摘要和相关产物。若证据或验证缺失，界面不得把结果标记为“可信”，而应显示明确限制。

## 8. 安全与错误处理

- 所有新增接口复用 `Action.ANALYSIS_RUN` 授权并强制工作空间隔离；
- SSE 在开始重放前完成鉴权，连接期间令牌过期由客户端重连处理；
- 服务端对事件 payload 和投影建立显式响应模型，不直接序列化 ORM 对象；
- 模型 `reasoning_content`、API Key、数据库凭据和原始敏感样例列入禁止响应字段；
- 前端错误按输入、权限、网络、模型配置、可重试运行和终态运行分类，提供可执行操作；
- 图表或 M7 报告能力未完成时不显示伪入口，M6 结果表格保持可用；
- 取消与终态事件竞态由后端现有状态机裁决，前端以最终投影为准。

## 9. 测试与验收

后端测试覆盖：任务列表分页与隔离、完整投影、SSE 历史重放、实时追加、心跳、终态关闭、`Last-Event-ID`、无权限访问、未知运行和敏感字段排除。

前端测试覆盖：事件解析与去重、投影归并、全部八种状态、各类用户操作、断线重连、令牌失效、空结果、部分结果、证据定位、未知事件和响应式布局。

Playwright 真实纵向验收至少包含：

1. 创建问题并观察真实任务事件；
2. 刷新后恢复到同一任务和最后事件；
3. 澄清或确认后继续执行；
4. 可恢复失败后重试；
5. 完成结果到 Evidence 定位；
6. 分析用户成功、无权限角色被阻断；
7. 桌面和窄屏核心流程可操作。

最终门禁包括 Ruff、严格 MyPy、Pytest、ESLint、TypeScript、Vitest、Playwright、迁移检查、Docker 镜像构建、Compose 健康检查和秘密扫描。

## 10. 实施切片

M6 按四个可独立验收的纵向切片实施：

1. M6-A：运行列表、完整投影和响应模型；
2. M6-B：可重放 SSE、Fetch 客户端和断线恢复；
3. M6-C：三栏工作台、状态操作和响应式交互；
4. M6-D：结果证据、真实浏览器验收、部署和阶段文档。

每个切片遵循测试先行、实现、全量回归、文档、精确提交和 GitHub 推送。用户已有未提交的 M3 验收文档始终排除在提交之外。

## 11. M6 与 M7 的明确边界

M6 的目标是让 M5 已有 Agent 闭环成为可靠可用的产品工作台。M7 才新增受限 ChartSpec/ECharts、高级描述统计、周期分析、Top N、相关性、异常检测，以及 Markdown、HTML、PDF 报告。M6 不预留“即将开放”的可点击假功能，也不为 M7 在前端复制计算逻辑。
