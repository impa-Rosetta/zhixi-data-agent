# A07 剩余产品交付设计规格

- 状态：待复核
- 日期：2026-09-06
- 适用范围：从当前 M2 前端收口状态推进至 M9 产品与比赛交付完成
- 基础规格：`docs/superpowers/specs/2026-09-04-a07-data-agent-design.md`
- 执行原则：纵向产品切片、确定性系统控制模型、每个切片可部署可验收

## 1. 目标与完成定义

目标是完成可私有化部署的制造业质量智能问析产品，而不是只展示固定问题的演示程序。用户应能接入未写死结构的 PostgreSQL 或 MySQL，确认语义映射，通过自然语言发起分析，由 Agent 选择受控工具执行真实查询和分析，最后获得表格、图表、结论、限制和可追溯证据。

整个项目只有在 M2 至 M9 的功能、自动化测试、真实数据链路、安全门禁、运行文档和比赛材料均完成后才标记完成。任何只有界面但没有真实后端结果、只有模型输出但没有工具证据、或只能适配固定表名的能力均不计为完成。

## 2. 实施路线

采用五阶段纵向路线，每阶段独立提交、部署和验收。

### 阶段 A：M2 数据治理控制台收口

交付结构差异、字段画像、安全采样策略、定时刷新计划、数据源编辑、凭据轮换、停用、启用和删除界面。完成 PostgreSQL 与 MySQL 的桌面、窄屏、异常、权限和恢复验收。

完成标准：管理员可仅通过 Web 完成从连接到目录、画像和刷新配置的完整流程；分析员只能读取授权目录和画像；任何凭据都不回显或进入客户端持久化状态。

### 阶段 B：M3 语义模型与 M4 安全查询内核

建立版本化制造质量语义模型、15 至 20 个可信指标、物理映射、候选映射确认和可复现合成数据。实现严格语义查询协议、指标编译器、SQLGlot 安全策略、行级约束、只读执行、超时、取消、结果限制和证据保存。

完成标准：同一语义问题可适配标准库、改名库和缺字段库；可信指标不依赖模型生成公式；危险 SQL 与越权对象阻断率为 100%。

### 阶段 C：M5 DeepSeek Agent 核心闭环

实现独立 Model Gateway、AnalysisRun 持久化状态、意图解析、语义绑定、声明式 Planner、Tool Registry、Plan–Execute–Verify 执行图和多轮上下文。

完成标准：低置信度进入澄清；服务重启后可恢复；相同幂等请求不重复执行关键步骤；模型不能修改指标口径、跳过权限或直接访问数据库。

### 阶段 D：M6 问析工作台与 M7 分析交付

实现 SSE 事件流、对话与任务、取消重试、计划确认、表格、ECharts 图表、统计与异常分析、三层验证、数字证据定位，以及 Markdown、HTML 和 PDF 报告。

完成标准：刷新不丢任务；图表或报告失败不丢查询结果；每个最终数字能定位到查询、指标版本、数据快照和验证记录。

### 阶段 E：M8 评测运维与 M9 产品交付

实现无网络、无凭据、资源受限的一次性 Python 沙箱；建立至少 140 组黄金场景；加入 Agent、模型、工具、SQL、队列和成本可观测性；完成性能、安全、备份恢复、升级回滚、部署运维文档和比赛材料。

完成标准：达到总设计中的准确率与安全阈值；完整环境可从空库部署、升级、备份和恢复；演示脚本使用真实数据和真实 Agent 链路。

## 3. 模块边界

### 3.1 Semantic Model

负责标准业务实体、指标、维度、关系、物理映射、版本、发布和可行性检查。该模块不调用模型、不执行 SQL。

### 3.2 Query Engine

输入已发布语义版本和严格查询协议，输出参数化 SQL、绑定参数、依赖对象和安全元数据。执行器只接受已验证查询 ID，不接受任意页面 SQL。

### 3.3 Model Gateway

封装 DeepSeek 官方接口、超时、重试、流式响应、结构化生成、工具调用、用量和错误分类。业务代码只能依赖网关协议，不能导入供应商 SDK。

### 3.4 Agent Core

持有 AnalysisRun 状态机、计划、预算、检查点、工具调用和重规划规则。Agent 只通过 Tool Registry 获取能力，不持有数据库凭据。

### 3.5 Toolkit

注册语义目录、指标查询、探索查询、统计、异常、图表、报告和治理能力。每个工具声明版本、JSON Schema、权限、风险、超时、重试、幂等和输出证据。

### 3.6 Analysis Engine 与 Sandbox

确定性分析优先在 Analysis Engine 执行。只有预注册能力无法覆盖的高级分析进入一次性沙箱；沙箱无网络、无数据库凭据，只读取裁剪后的只读输入。

## 4. 主数据流

```text
用户问题
→ 创建 AnalysisRun 和幂等消息
→ 意图解析与已发布语义版本绑定
→ 生成声明式 AnalysisPlan
→ Policy Engine 与预算检查
→ Tool Registry 解析能力实现
→ 语义查询编译或受控探索 SQL
→ AST、安全、成本和对象权限校验
→ 只读执行与结果脱敏
→ 统计/异常/图表工具
→ 结构、数据和语义验证
→ 证据与产物原子持久化
→ SSE 输出进度和最终答案
```

每个外部副作用之前保存计划和幂等键，每个节点之后保存检查点。最终答案不能先于验证和证据提交。

## 5. DeepSeek V4 Pro 接入

- 官方 Base URL：`https://api.deepseek.com`；
- 默认模型 ID：`deepseek-v4-pro`；
- 采用 OpenAI-compatible Chat Completions 作为首发稳定协议；
- 意图分类、语义绑定和短结构化任务使用非思考模式；
- 复杂计划、探索 SQL 修正和报告综合使用思考模式；
- 思考模式工具循环必须完整回传 `reasoning_content`；恢复所需内容只进入加密的活动检查点，禁止进入日志、普通Trace和前端，并按运行保留策略清理；
- JSON 输出和工具参数均经过本地 Pydantic/JSON Schema 二次校验；
- 首发不依赖 Beta strict endpoint，避免产品核心路径绑定 Beta 行为；
- API Key 只从 `DEEPSEEK_API_KEY` 或部署 Secret 读取，不保存到数据库、前端、日志、Trace、测试快照或 Git；
- 测试默认使用协议级 Fake Gateway，真实模型验收由显式开关触发并限制预算；
- 模型不可用时保留已完成查询和产物，运行进入可恢复失败状态，不伪造答案。

## 6. Agent 工具集合

首版工具控制在以下能力，不向模型暴露内部实现碎片：

1. `catalog.search`：检索已授权目录；
2. `semantic.resolve`：解析术语、指标和维度候选；
3. `query.metric`：执行可信指标查询；
4. `query.explore`：执行经过完整安全流程的探索查询；
5. `analysis.describe`：描述统计与数据质量；
6. `analysis.compare`：同比、环比和分组比较；
7. `analysis.rank`：Top N 与贡献分析；
8. `analysis.correlate`：相关性分析并附因果限制；
9. `analysis.detect_anomaly`：规则与 Isolation Forest 异常检测；
10. `visualization.compose`：从已验证数据生成受限 ChartSpec；
11. `report.compose`：从已有产物组装报告；
12. `run.request_confirmation`：请求用户确认高影响计划或歧义。

工具输出使用结构化 ArtifactRef 和 EvidenceRef，避免把大结果反复放入模型上下文。

## 7. 数据与版本策略

语义模型、指标、物理映射、工具、提示模板和评测集均版本化。AnalysisRun 在创建时冻结数据源目录快照、语义版本、指标版本和工具版本。后续发布的新版本不会改变正在运行或已完成任务的含义。

查询结果和模型上下文只保留必要字段、摘要和受控样例；敏感字段使用现有确定性识别和脱敏策略。大结果写入对象存储，状态库只保存摘要、校验和及引用。

## 8. 错误处理

错误分为输入歧义、语义不可用、权限拒绝、查询安全、数据质量、模型暂态、模型永久、工具暂态、资源预算和平台内部错误。

- 歧义和低置信度：暂停运行并请求用户确认；
- 权限、安全和预算错误：立即终止，不允许模型重试绕过；
- 模型限流、网络错误和工具瞬时错误：在幂等边界内指数退避；
- SQL 修正最多两次，重新规划最多一次；
- 查询、图表或报告失败分别保留之前已经验证的产物；
- 面向用户返回可行动说明，内部记录脱敏错误码和关联 ID；
- 任何异常都不得把密钥、凭据、原始敏感样例或完整思考内容写入日志与普通Trace；活动检查点中的受限推理状态按上一节规则处理。

## 9. 前端产品结构

保留混合式企业工作台：

- 智能问析：问题、多轮上下文、计划、进度、结果、图表和证据；
- 数据源：连接、目录、差异、画像、采样和刷新；
- 语义与指标：候选映射、冲突确认、指标编辑、可行性和发布；
- 分析任务：运行历史、恢复、取消、重试和技术详情；
- 评测中心：黄金集、准确率、安全、延迟和成本；
- 审计运维：权限、工具、模型调用、查询和系统健康。

业务默认视图不显示复杂技术细节，SQL、Trace、模型、工具和版本按需展开。

## 10. 测试与质量门禁

每个切片至少包含单元测试、契约测试、权限与错误测试、前端组件测试和一条真实纵向验收。涉及数据库方言时必须同时覆盖 PostgreSQL 与 MySQL；涉及模型时默认使用可复现 Fake Gateway，并设置少量显式真实 DeepSeek 验收。

合并门禁包括 Ruff、严格 MyPy、Pytest 覆盖率、ESLint、TypeScript、Vitest、Playwright、迁移往返、镜像构建、依赖与秘密扫描。Agent 阶段加入黄金集回归，严重安全失败一票否决，不能被平均分掩盖。

## 11. 提交与部署策略

每个纵向切片遵循：

1. 测试先行并确认失败原因；
2. 实现最小完整产品能力；
3. 运行静态检查、全量测试和真实链路；
4. 更新 ADR、项目状态和验收记录；
5. 构建并部署本地 Compose；
6. 仅暂存本切片文件；
7. 提交并推送 GitHub；
8. 验证远端提交与运行服务一致。

用户已有未提交文件不自动覆盖或纳入提交。任何高风险外部写入、公开部署、付费模型批量评测和不可逆数据操作均单独控制范围。

## 12. 首批后续切片

按以下顺序开始执行：

1. M2 结构差异界面；
2. M2 字段画像界面；
3. M2 采样策略与定时刷新；
4. M2 数据源编辑、凭据轮换、启停与删除；
5. M2 双数据库与响应式整体验收；
6. M3 标准质量语义模型基础；
7. M3 指标中心与物理映射；
8. M4 语义查询协议与安全执行内核；
9. M5 Model Gateway 和 Agent 最小闭环；
10. 按阶段 C 至 E 继续扩展直至全部完成。

每一项都以真实运行结果和验收证据结束，不以静态页面或模拟回答代替。
