# M6.1 Agent 路由与自然澄清设计

- 状态：待用户审阅
- 日期：2026-09-09
- 上游：M5 Agent 核心闭环、M6 智能问析工作台
- 后续：M7 分析、图表与报告

## 1. 背景与问题

M6 已经打通 DeepSeek 意图解析、发布语义绑定、安全查询、持久化结果和 Evidence，但当前运行时把所有请求都收敛到单个 `query.metric` 步骤。工具注册表虽然已有 `catalog.search`、`semantic.resolve` 和分析类工具定义，Planner 与执行器尚未按任务类型路由。

真实使用暴露出三类问题：

1. “这是个什么 Agent”属于能力咨询，却被当成缺少指标的分析问题；
2. “表格中有什么数据”属于目录探索，却没有进入目录工具；
3. “分析不良率”已经能够唯一识别指标，但因为缺少可选时间和维度、置信度略低而被强制澄清。

M6.1 的目标是让入口具备产品级任务分流和自然澄清能力，同时保留已有的确定性执行、安全门禁、预算、恢复和审计边界。M6.1 不实现 M7 的统计、异常检测、图表或报告算法。

## 2. 设计原则

- 模型负责理解自然语言，不负责授权、物理绑定、SQL 或工具执行裁决；
- 路由结果必须通过严格 Pydantic/JSON Schema 验证；
- 每类任务只能进入显式允许的本地处理器或工具；
- 能用安全默认值完成的问题不要求澄清；
- 只有会改变口径、对象或权限边界的歧义才暂停运行；
- 所有面向用户的回答均持久化为 Artifact，并能追溯 Evidence 或明确标记为静态产品信息；
- 运行投影与 SSE 契约保持向后兼容，旧客户端可以忽略新增 Artifact 类型和事件字段。

## 3. 任务分类与路由

### 3.1 严格任务类型

将现有 Intent 的任务类型扩展为以下路由：

| 路由 | 典型问题 | 执行方式 | 数据访问 |
|---|---|---|---|
| `capability_help` | 这是什么 Agent、你能做什么、怎么使用 | 本地能力清单模板 | 无 |
| `catalog_exploration` | 有哪些数据、有哪些表、某表有哪些字段 | `catalog.search` | 已授权目录快照 |
| `metric_query` | 分析不良率、查询合格率 | `semantic.resolve` 后 `query.metric` | 可信语义查询 |
| `comparison` | 同比、环比、组间对比 | M6.1 只完成路由与能力提示，M7 接入执行 | 不提前伪造 |
| `ranking` | 哪条产线最高、Top N | M6.1 只完成路由与能力提示，M7 接入执行 | 不提前伪造 |
| `trend` | 最近三个月趋势 | M6.1 只完成路由与能力提示，M7 接入执行 | 不提前伪造 |
| `unsupported` | 与企业数据分析无关或需要禁止能力 | 给出范围说明和可行动建议 | 无 |

模型输出 `Intent` 候选后，本地 `RoutePolicy` 根据任务类型、指标、维度、歧义种类、发布语义模型和授权目录确定唯一处理路径。模型不能通过输出工具名绕过该策略。

### 3.2 路由顺序

1. 校验 Intent Schema、预算和运行权限；
2. 对能力咨询和明显越界问题走无数据本地回答；
3. 对目录探索确定授权快照与搜索范围；
4. 对指标任务执行确定性语义解析；
5. 对尚未实现的 M7 高级分析返回明确能力状态，不显示伪结果；
6. 仅在存在阻断性歧义时进入 `waiting_for_clarification`。

## 4. 自然澄清策略

### 4.1 阻断性与非阻断性歧义

以下情况必须澄清：

- 指标名称能映射到多个已发布口径；
- 用户明确要求某对象，但目录中存在多个同名候选且无法唯一定位；
- 查询必须具备的过滤值缺失；
- 请求跨越多个数据源或语义版本，无法形成单一可信执行边界；
- 用户要求的时间比较无法确定基期或当前期。

以下情况采用默认值继续：

- 普通指标查询未指定时间范围：使用该指标当前语义版本可查询的全部范围；
- 未指定维度：返回整体指标；
- 未指定输出形式：单行优先指标卡，多行优先表格；
- 模型置信度略低，但指标和维度已被本地唯一解析且不存在阻断性歧义。

置信度不再单独作为暂停条件。低置信度只进入审计和可观测信息；最终能否执行由确定性解析结果与阻断性歧义决定。

### 4.2 结构化澄清请求

新增 `ClarificationRequest` 契约：

- `reason_code`：稳定机器错误码；
- `question`：面向用户的具体问题；
- `missing_fields`：真正缺失的必要项；
- `candidates`：安全、有限、已授权的候选；
- `suggested_answers`：最多三个可直接采用的回答；
- `resume_node`：补充后恢复的确定性节点。

`run.clarification_required` 事件携带该安全投影，运行上下文保存完整结构。前端展示具体问题和候选，不再显示无法行动的通用提示。

### 4.3 多轮上下文合并

用户补充信息时不再整体丢弃已有 Intent。新消息解析为受限 `ContextPatch`，本地合并 metrics、dimensions、filters、time_range、comparison 和 output；随后重新运行 RoutePolicy 与绑定。若用户明确更换任务目标，则创建新 Intent 修订并留下事件记录。旧计划和绑定不能跨目标复用。

## 5. 处理器与工具边界

### 5.1 能力咨询处理器

能力回答来自版本化的本地 `CapabilityManifest`，包含当前已开放能力、可信边界、使用示例和暂未开放能力。模型可以负责语言润色，但首版优先使用确定性中文模板，避免能力幻觉和额外模型成本。

输出：

- `assistant_message` Artifact；
- `capability_manifest` Evidence，记录清单版本；
- `capability_scope` Validation，证明回答未声明清单外能力。

### 5.2 目录探索处理器

`catalog.search` 只查询当前工作空间可访问数据源的已发布目录快照。支持数据源、Schema、表/视图和字段级检索，并返回有限的结构摘要。字段样例只有在采样策略允许时返回，且继续使用现有敏感识别与脱敏结果。

输出：

- `catalog_result` Artifact；
- 一个或多个 `catalog_snapshot` Evidence；
- `authorization_scope` 与 `sensitive_output` Validation。

目录工具不接受任意 SQL，不访问未发布快照，不返回连接凭据、系统表或未脱敏敏感样例。

### 5.3 指标查询处理器

指标路径仍复用 M4/M5 的可信查询链路。变化仅限于：

- 先通过 `semantic.resolve` 产生确定性候选；
- 唯一解析后再构造 `query.metric`；
- 可选条件缺失时应用并记录默认范围；
- 结果、Evidence、Validation 和冻结版本格式保持兼容。

## 6. 持久化与 API

优先复用现有 `analysis_runs`、`analysis_messages`、`analysis_plans`、`analysis_steps`、`analysis_tool_calls`、`analysis_artifacts`、`analysis_evidence`、`analysis_validations` 与 `analysis_events`，不为任务路由新建平行状态库。

运行上下文新增版本化字段：

- `intent_revision`；
- `route`；
- `clarification`；
- `defaults_applied`；
- `capability_manifest_version`。

新增事件类型：

- `run.route_selected`；
- `run.defaults_applied`；
- `run.intent_revised`。

现有 Run View API 继续返回 Artifact/Evidence/Validation；新增结构只允许输出经过白名单序列化的安全字段。无需新增 WebSocket 或第二套会话接口。

## 7. 前端交互

问析工作台根据 Artifact 类型增加两类正式呈现：

- `assistant_message`：以 Agent 消息卡显示能力范围、示例和限制；
- `catalog_result`：显示数据源、表/视图、字段数量、字段摘要、快照时间和脱敏说明。

澄清卡显示具体问题、候选快捷按钮和自由文本输入。用户选择候选后仍通过现有幂等消息接口提交，刷新和断线恢复行为不变。

高级分析尚未实现时，系统明确告知“基础指标查询已可用，该分析类型将在 M7 工具链中执行”，但不会把运行标成成功数据结果。M7 接入后替换对应处理器，不修改页面路由和持久化基础。

## 8. 错误处理与安全

- 无已发布目录：返回可行动的 `catalog.not_available`，指引先完成元数据扫描；
- 无已发布语义：返回具体的语义模型指引，不进入无限澄清；
- 目录候选过多：返回总数与有限候选，要求缩小范围；
- 权限拒绝：立即失败并记录审计，不让模型重试规避；
- DeepSeek 暂态失败：沿用现有幂等、预算和可恢复失败策略；
- Schema 失败：沿用一次受控纠正，失败后不放宽契约；
- 所有错误投影禁止包含 API Key、数据库凭据、原始敏感样例和受限推理。

## 9. 测试与验收

### 9.1 单元与契约测试

- 路由分类和 RoutePolicy 决策矩阵；
- 阻断性/非阻断性歧义；
- ContextPatch 合并与目标切换；
- CapabilityManifest 不越界；
- 目录搜索授权、快照、数量上限与脱敏；
- 新 Artifact、Evidence、Validation 和事件的安全序列化。

### 9.2 集成测试

- Fake Gateway 覆盖能力咨询、目录探索、指标查询和真正歧义；
- PostgreSQL 与 MySQL 目录搜索；
- “分析不良率”无时间维度时直接完成；
- 多轮补充保留前一轮指标；
- 无目录、无语义、重名候选、权限拒绝和模型失败。

### 9.3 产品验收问题

- “这是个什么 Agent”；
- “你能做什么”；
- “有哪些数据源”；
- “表格中有什么数据”；
- “inspection 表有哪些字段”；
- “分析不良率”；
- “按产线分析不良率”；
- 一个真实多口径问题，必须展示具体候选并等待选择。

桌面 1440×1000 和移动 390×844 均需通过创建、SSE 更新、刷新恢复、自然回答、目录卡片、快捷澄清和无横向溢出验收。真实 DeepSeek 验收使用显式开关和受限预算，默认 CI 使用 Fake Gateway。

## 11. 完成定义

M6.1 只有同时满足以下条件才算完成：

- 三类已开放任务能够选择正确处理器并产生持久化回答；
- 普通指标查询不再因可选条件缺失而无意义阻塞；
- 真正歧义提供具体、可操作、可恢复的澄清；
- 能力和目录回答不包含未授权、未脱敏或模型虚构内容；
- 全量后端与前端质量门禁通过；
- PostgreSQL/MySQL、桌面/移动端和真实 DeepSeek 链路通过验收；
- 技术决策、项目状态、验收记录与 GitHub 提交同步更新。
